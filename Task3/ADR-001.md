### <a name="_qmphm5d6rvi3"></a>**Решение**
Для реализации MVP создается новый компонент — «Сервис депозитных заявок». Это отдельный микросервис, который будет служить единой точкой входа для всех онлайн-заявок на депозиты. Данное решение позволяет изолировать фронтальные системы от внутренних систем банка (в первую очередь, от перегруженной АБС) и сделать первый шаг к микросервисной архитектуре, не нарушая существующих ограничений.

#### [Диаграмма контекста C4](https://github.com/kotenev/architecture-pro-standart/blob/standart/Task3/ADR-001/(TO-BE)%20Standart_Deposit_C4_Context.puml)

На уровне контекста выделяются следующие системы: Сайт, Интернет-банк, Система кол-центра, АБС и новый центральный компонент — Сервис депозитных заявок. Клиенты взаимодействуют с Сайтом и Интернет-банком, которые, в свою очередь, общаются с новым сервисом по REST API. Сервис депозитных заявок интегрируется с Системой кол-центра (для заявок с сайта) и асинхронно передает данные в АБС для дальнейшей обработки сотрудниками бэк-офиса.

#### [Диаграмма контейнеров C4](https://github.com/kotenev/architecture-pro-standart/blob/standart/Task3/ADR-001/(TO-BE)%20Standart_Deposit_C4_Container.puml)

Новый сервис будет состоять из следующих контейнеров:
1. API-приложение (Java/Spring Boot): stateless-сервис, предоставляющий REST API для фронтальных систем. Он реализует всю бизнес-логику по приему, валидации и сохранению заявок.
2. База данных (PostgreSQL): собственное хранилище сервиса для хранения всех поступающих заявок.
3. Интеграционный шлюз с АБС: компонент, отвечающий за асинхронную передачу заявок в АБС. Для MVP это будет реализовано через запись в Промежуточную БД (MS SQL), откуда данные будут забираться пакетным процессом со стороны АБС.

#### Логика принятия решений и выбор технологий:

- Выделение в микросервис: это решение продиктовано ключевыми требованиями: необходимостью изоляции от АБС (P2, +R8), стратегией перехода на микросервисы (+R4) и требованием не дорабатывать ядро интернет-банка силами подрядчика (+R6).
- Технологический стек (Java/Spring Boot): выбран на основе существующей экспертизы в банке (+R3). Команды, поддерживающие АБС и систему кол-центра, имеют опыт в Java-стеке, что упростит разработку и поддержку.
- Асинхронная интеграция через Middleware БД: это простой и надежный для MVP паттерн, позволяющий гарантированно отделить онлайн-нагрузку от АБС. Он не требует несовместимых с текущей инфраструктурой технологий (как Kafka) и реализуется силами команд банка.
- Безопасность (+R1): все внешние взаимодействия с сервисом будут происходить по REST API с использованием шифрования (JSON/HTTPS).

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Прямая интеграция с АБС через API: разработка API на стороне АБС для приема онлайн-заявок.
    - Причина отказа: критически высокий риск нарушения стабильности работы АБС из-за неконтролируемой онлайн-нагрузки. Противоречит ограничениям P2 и +R8.
2. Реализация логики в ядре интернет-банка: доработка существующего монолита интернет-банка силами подрядчика.
    - Причина отказа: противоречит стратегическому решению об отказе от доработок подрядчиком (+R6), ведет к усилению vendor-lock и усложнению монолита, что противоречит курсу на микросервисную архитектуру (+R4).

**Недостатки, ограничения, риски**

- Неполная автоматизация: решение не обеспечивает мгновенное открытие депозита. Процесс остается зависимым от ручной обработки заявок сотрудниками бэк-офиса.
- Задержка в обработке: из-за асинхронной пакетной интеграции возникает задержка между подачей заявки клиентом и ее появлением в АБС.
- Операционная сложность: внедрение нового сервиса увеличивает сложность IT-ландшафта и требует выделения ресурсов на его поддержку, мониторинг и развертывание.
- Риск интеграции: реализация и поддержка пакетного процесса импорта данных из промежуточной БД в АБС может оказаться сложной и стать точкой отказа.
- Зависимость от команды АБС: успех решения зависит от своевременной реализации интеграционного job-а на стороне команды АБС.
